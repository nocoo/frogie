# 06 - Tests

## 验证目标

测试证明 Frogie 自己的定义、接入、权限和界面行为可靠；真实模型 Evaluation 证明定义能驱动 Pi Durable 完成工作。两类验证共用运行端、定义和产物协议，各自检查最适合自己的边界。

首期完整落实 6DQ L1，并为 MVP 增加少量必要的真实 Pi 集成和浏览器验收。每个用例对应一个具体风险，业务场景由 [Evals](07-evals.md) 集中维护。

## 6DQ 分工

| 维度 | 本项目的职责 | 首期执行方式 |
| --- | --- | --- |
| L1 | 单元测试、四项覆盖率、严格静态检查、提交拦截 | 每次提交检查 Git 暂存快照 |
| L2 | 模块与协议集成 | 用真实 Pi、SQLite 和受控进程验证少量关键边界 |
| L3 | 完整用户路径 | 用浏览器贯穿定义编辑、调试、观察与产物 |
| G2 | 安全检查 | 权限、路径、认证和沙箱风险先落实到对应测试；依赖与密钥扫描随推送门禁建设 |
| D1 | 测试数据与环境隔离 | 所有层次从首个用例开始执行 |

L1 是首期质量门槛，选定的 L2、L3 和真实评估是 MVP 的产品验收材料。6DQ 各维度按实际执行证据分别记录。

## 测试工具与目录

采用 Vitest 组织确定性测试，V8 提供覆盖率，Playwright 负责浏览器路径。模型使用 Pi `Models` 接口的可编程假实现，工具使用独立临时数据；集成测试保留真实 Pi Harness 和存储。

```text
packages/core/src/**/*.test.ts
apps/dashboard/src/**/*.test.ts
tests/
  fixtures/
    minimal-squad/
  integration/
  e2e/
evals/
  ...
```

模块单元测试就近放置；跨模块、子进程和浏览器测试分别进入 `tests/integration/` 与 `tests/e2e/`。定义脚本与评估断言的确定性测试靠近其源码。`minimal-squad` 只提供解析、角色装配和接入所需的最小内容。

工程初始化时在根 `package.json` 提供单元测试及覆盖率、集成测试、浏览器测试、L1 和推送检查入口，精确命令同步到根 `AGENTS.md`。真实模型评估使用独立入口。

## L1：按风险覆盖行为

| 边界 | 主要断言 |
| --- | --- |
| 定义解析 | 字段、唯一主控、嵌套角色、ID 与引用正确；重复键、断链、越界路径和符号链接被定位 |
| 工作流图 | 节点、入口、边、正文与角色引用一致；同角色多步骤和复核回路可解析；图与 MD 往返、执行指导渲染稳定 |
| 版本与编辑 | 文件或脚本改变影响摘要；顺序规范化稳定；外部修改触发保存冲突；错误候选保持原文件 |
| 角色装配 | 默认值、角色值和获准微调正确；实际模型与思考等级可解析；子角色具有自己的明确配置 |
| 权限 | 工具、Workflow 与宿主授权取交集；Extension 名称与工具实现匹配；未获准操作在执行入口失败 |
| 公共协议 | Pi 状态原样映射；快照替换、重连、错误、分页和产物引用的归属检查正确 |
| ViewModel | 图编辑与撤销、节点和角色草稿、校验、提交重试的 `requestId`、排队与停止、会话切换和断线恢复符合用户动作 |
| 宿主边界 | argv 构造、重放准入、输入限制、超时、输出上限、产物回执、清理归属和持久预算正确 |
| 脚本与评分 | 计算和业务断言覆盖正常、边界与无效输入；断言失败可以指向具体证据 |

相同规则以表驱动用例覆盖等价类。测试断言结果、错误和可观察副作用，辅助结构按真正需要复用。

### 覆盖范围

覆盖率纳入 Core 运行代码、Dashboard 的 Model／ViewModel／服务端／运行端代码、Squad 可执行脚本和评估断言。纯展示 View、类型声明、生成物和第三方代码单独列明在配置中。

语句、分支、函数和行四项均达到 95%。报告保留公共包、Dashboard 与脚本／评估代码的归属；子进程执行证据由相应测试记录，父进程覆盖率只反映实际被插桩的代码。

测试中全部必需用例执行，必需套件为空、被跳过或被聚焦筛选时检查失败。模块导入成功和快照数量分别作为辅助信息，行为断言构成主要证据。

### 静态检查

TypeScript 启用 `strict` 并执行类型检查；JavaScript 脚本纳入对应的类型或语法检查。统一使用 Biome 的明确规则和只读格式检查，警告同样导致失败。

文档检查覆盖相对链接、索引完整性和约定格式；定义检查读取全部 Squad，校验文件、引用和脚本声明。模型服务连通性留给运行预检。

## L2：三个接入边界

### 1. 绑定、投递与观察

使用真实 Pi 和 MemoryStorage 加载最小 Squad，通过公共入口创建主控及两个同角色的独立会话。可编程模型按输入返回固定响应或工具调用。

在一条可追踪链路中检查：

- 角色装配、会话身份及有效工具范围。
- 相同 `requestId` 的重复投递取得同一 Submission。
- busy 时的 follow-up、steer 和 reject，以及排队撤回。
- 前台派发的子会话所有权、真实答复回传和向下取消。
- 观察者中途连接、断开和重新取得快照，状态与 Harness 当前值一致。

将这组行为组织为公共包的 `testing` 入口，接受集成方的宿主创建与释放函数。本地参考端与独立最小宿主都运行该组符合性检查；宿主只需替换业务 Tool 和环境配置。

### 2. SQLite 与进程恢复

使用 Node SQLite 原生适配器、独立数据库和真实子进程。控制器在明确的持久化边界等待信号，然后终止自己创建的 Harness 进程，再由新进程打开原存储。

围绕一次“父会话派发 → 子会话调用工具 → 回传结果”检查两个必要窗口：

| 中断点 | 必须成立的结果 |
| --- | --- |
| 子会话已创建且输入已接纳 | 恢复使用原 Conversation、Submission 与所有权关系 |
| 可重放工具已保存幂等回执，Pi tool result 尚未提交 | 工具重新进入后读取原回执，外部效果保持一次 |

同一恢复材料另检查默认 unsafe 工具的中断语义：出现 Pi 的 `interrupted` 结果，实际调用次数保持原值。缺失 Extension 或定义摘要不匹配的启动预检也在此边界验证。

断言读取数据库、任务记录、外部回执和最后答复；控制器按信号同步，有界等待。数据库所有权检查保证第二个宿主无法同时使用它。

使用 Pi 官方存储适配器时，Frogie 测试自己的接入与恢复契约。集成方编写自有 Storage 时，额外运行 Pi 提供的 `registerStorageConformance()`；自有 ExecutionEnv 使用对应的 `registerEnvConformance()`。

### 3. 本地宿主安全边界

对 HTTP 文件服务和实际 Docker 脚本执行器运行一组独立检查：未授权来源、错误会话归属、路径逃逸和保存冲突均保持边界；脚本能够读取指定输入，同时只能写自己的临时空间。

沙箱用例使用虚构数据和哨兵文件，验证宿主私有文件、凭据和外部网络不可达，资源超限与取消能结束整个调用，其他环境和容器保持原样。测试记录实际容器参数与结果。

Docker 不可用时环境预检失败并说明原因。沙箱集成验收以真实执行证据为准，L1 的参数测试继续独立运行。

## L3：一条界面主路径

浏览器连接真实 Dashboard 服务和本地宿主，模型使用可编程假实现。主路径复用同一个最小 Squad：

1. 打开项目，进入角色，编辑提示词、保存并看到新的校验与摘要。
2. 创建绑定，完成预检，进入主控会话并发送输入。
3. 展开一次子会话和工具调用，查看结果产物。
4. 刷新页面后重连，确认历史和运行状态来自原环境。
5. 在评估页打开同格式报告，定位断言证据。

完整业务机制由 L1／L2 覆盖，浏览器只检查用户能否操作与理解这些状态。围绕关键交互补充小型组件用例：输入法发送、草稿保存冲突、错误重试、停止、焦点恢复和窄屏主从切换。

视觉验收使用实际发布的 Basalt 包，检查 390px 和 1440px 视口、浅深主题、键盘路径与 reduced-motion。截图聚焦完整工作台与关键状态，保留 logo、表面层级和内容可读性。

真实模型验收通过 Evals 的同一入口运行。用户可以从 Dashboard 发起和观察该运行，浏览器脚本保持确定性。

## 门禁与隔离

Pre-commit 和 pre-push 以 [开发约定](02-repository-and-workflow.md) 为准。实现时保留一个只读检查入口，hooks 与 CI 调用它，检查对象分别为暂存快照和实际推送 SHA。

门禁在独立 Git fixture 中证明以下事实：健康快照可通过，测试失败、任一覆盖率不足、类型错误、lint 警告、缺工具、空报告和超时会拦截提交；未暂存修复无法掩盖暂存错误。执行结束后工作区、暂存区与无关进程保持原样。

每次测试生成唯一工作目录、环境 ID、数据库、端口与容器标签。环境变量按白名单提供虚构值，模型和业务服务使用本次测试的隔离实例。清理先检查所有权，范围限定为本次创建的资源。

常规 L1 的目标为 30 秒内，推送检查目标为 3 分钟内；实现后报告实际耗时和完整检查结果。真实模型评估与需要 Docker 的完整沙箱验收由独立显式入口执行。

## TDD 与原子交付

按可运行的纵向能力组织实现，每一段同时交付执行入口与可操作界面：

| 顺序 | 最小可用能力 | 主要验证 |
| --- | --- | --- |
| 1 | 读取定义，在 Basalt 工作台查看角色并完成一次会话输入输出 | 解析与配置 L1、最小接入、浏览器主路径起点 |
| 2 | 编辑并冻结定义，派发子会话，执行受控脚本并查看产物 | 权限、编辑、工具 L1，派发与沙箱 L2 |
| 3 | 观察、取消、断线重连、SQLite 重启恢复 | 状态 L1、持久化 L2、浏览器路径补全 |
| 4 | 完整 Squad 与真实评估报告在 Dashboard 中闭环 | 评分 L1、真实评估和人工 UI 验收 |

每个行为先写预期失败的测试，再实现最小通过路径，最后整理；代码、相应测试与必要文档原子提交。报告区分执行过的测试、覆盖率、人工验收和真实模型结果，证据关联实际代码与定义版本。

## MVP 完成条件

L1 的全部检查通过并能拦截失败，关键 Pi 接入与进程恢复具有真实证据，完整 Dashboard 路径可以操作，脚本隔离经过实际验证，真实行为评估取得独立报告。问题由失败断言定位到定义、公共接入、宿主、界面或模型行为，供下一轮 TDD 修正。
