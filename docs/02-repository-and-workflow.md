# 02 - 仓库结构与开发约定

本文约定 monorepo 的初步模块划分和共同开发原则。各模块的内部目录、接口与文件格式在后续设计文档中细化，相关文档通过 [文档索引](README.md) 持续维护。

## 仓库划分

采用 workspace monorepo，首期设置一个公共包和一个 Dashboard 应用。根目录统一管理工作区、单一依赖锁文件和开发命令，各工作区声明自己的依赖与公开入口。

| 目录或文件 | 初步职责 |
| --- | --- |
| `apps/dashboard/` | 本地 Dashboard、启动入口及调试运行端，提供管理、观察和调试能力 |
| `packages/core/` | 定义解析、公共协议、Pi 接入、权限、观察和界面集成等可复用能力 |
| `squads/` | 纳入 Git 管理的 Squad 定义、角色、技能、工作流和配套脚本 |
| `seeds/` | 纳入 Git 管理的初始化入口、样例选择与确定性模型材料，引用 Squad 和评估输入 |
| `data/` | Git 忽略的本机 Local、E2E、Prod 数据库、定义快照、运行产物和报告 |
| `tests/` | 跨模块集成测试、完整流程测试及公共测试材料 |
| `evals/` | Agent 行为评估用例与执行入口 |
| `scripts/` | 仓库开发、构建和检查工具 |
| `.husky/` | Git hooks 的调用入口 |
| `docs/` | 持续维护的文档索引和编号设计文档 |
| `assets/brand/`、`logo.png` | 视觉标识原图、来源记录与相关资产 |
| `AGENTS.md` | 项目工作规则与文档发现入口 |
| `README.md` | 面向用户的项目概述 |
| `Retrospective.md` | 操作复盘和经验记录 |

Dashboard 通过公共包接入 Pi Durable，本地调试端与集成方复用相同能力。依赖方向为应用依赖公共包，公共包依赖 Pi；Pi 相关依赖统一版本。

上述目录按功能实现逐步建立。公开入口和模块内部划分随相关设计确定。

## Dashboard 采用 MVVM

| 层次 | 职责 |
| --- | --- |
| Model | 领域数据、业务规则和服务访问 |
| ViewModel | 页面状态、用户操作和异步协调，向 View 提供可观察的数据与动作 |
| View | 页面布局、组件展示和交互绑定 |

界面业务行为放在 Model 和 ViewModel 中，通过单元测试验证。View 消费 ViewModel，完整用户交互通过端到端测试验证。授权由服务端和运行端执行，界面根据结果呈现可用操作。

## TDD 开发

采用测试驱动开发：先编写用例并确认预期失败，再实现使其通过的最小功能，最后在测试保护下整理代码。

- 单元测试与被测模块就近组织，覆盖正常、边界和失败行为。
- 公共协议变更同步维护符合性测试，本地调试端和集成方复用相同验证机制。
- 定义变更验证解析结果和引用关系，界面行为变更验证对应 Model 与 ViewModel。
- Evaluation 通过固定输入和验收条件验证 Agent 行为，结果关联所用定义版本。

首期落实 6DQ 的 L1，MVP 同时覆盖必要的 L2 接入与恢复、从零搭建完整 Squad 的 L3 E2E。G2 安全检查随功能与门禁建设补充，D1 的测试隔离原则贯穿各层。

## 数据与验证环境

定义、脚本、seed 生成源码及其输入随 Git 管理。生成的数据库、历史、恢复数据与报告保存在工作区的 `data/`，根 `.gitignore` 忽略整个目录；启动器按需创建子目录。

本地应用提供 Local、E2E、Prod 三种模式，每种模式的数据库都在本机，使用相同应用代码、Core 协议和 Pi 存储。Local 与 Prod 分别保存自己的长期运行数据；E2E 为每次验证创建独立定义工作区与运行数据。具体目录、切换和归属检查见 [Dashboard](04-dashboard.md)。

`squads/` 是共享定义源，运行端加载其不可变快照。E2E 的文件编辑只作用于本次隔离工作区。seed 的空白与样例配置共用受控初始化入口，重新启动保留已有数据；重置按明确选择和资源归属执行。

测试使用模拟模型、工具与凭据，每次运行创建独立的本地数据和进程环境。自动 E2E 由启动器锁定在本次资源范围，初始化、重置和清理前核对测试标识与资源归属。真实模型评估使用显式授权的独立 Local 环境。

凭据保存在本机私有配置中。构建产物、覆盖率和运行报告放入忽略的生成目录或测试临时目录。

## 原子化提交

每次完成一个逻辑变更并验证通过后立即提交。提交前检查差异，使用显式文件路径暂存，保留正常 Git hooks。

提交信息使用英文 Conventional Commits，采用小写祈使句，长度不超过 50 个字符。代码、对应测试和必要文档作为同一逻辑变更提交。

## Pre-commit

提交前执行 L1，检查对象为 **Git 暂存快照**，包含源码、定义、配置和测试。

- 执行完整单元测试及覆盖率检查，语句、分支、函数、行四项分别达到 95%。
- 执行严格类型、lint 和格式检查，要求零错误、零警告，并校验文档与定义。
- 测试失败、覆盖率不足、必需用例为空或遗漏、缺少必需工具和超时均拦截提交。
- 检查只读执行，工作区和暂存区保持原样；正常代码改动的检查目标为 30 秒内。

Squad 的 MD 和技能脚本属于行为定义，接受相应检查。Husky 与根目录检查入口在工程初始化时建立，具体命令随实现记录在 `AGENTS.md`。

## Pre-push

推送前检查 **实际待推送的提交**。入口依据 Git hook 标准输入中的 ref 和 SHA 确定检查范围，在独立快照上验证对应内容，并覆盖多 ref、新分支和分支删除等情况。

首期复核目标提交的 L1 与构建。后续将 L2 和 G2 纳入推送检查，分别验证集成行为、目标锁文件依赖和待推送内容及其引入历史中的密钥，常规执行目标为 3 分钟内。所有必需检查成功后才允许推送。

L3 的完整搭建路径是 MVP 必需的 CI 验收项，也提供显式手动入口。手动检查、hooks 和 CI 复用检查逻辑，实际命令以根目录 `package.json` 和项目工作规则为准。

### 首期检查入口

| 入口 | 检查对象与内容 | 执行条件 |
| --- | --- | --- |
| Pre-commit | 暂存快照的完整 L1 | 本机确定性检查，独立于 Docker 与真实模型 |
| Pre-push | 实际待推送 SHA 的完整 L1 与构建 | 隔离快照，全部必需检查通过 |
| MVP CI | 目标版本的 L1、构建、选定的真实 Pi L2 与完整搭建 L3 | 提供 Docker 和确定性模型，保留版本与定义证据 |
| 真实 Evaluation | 获准定义与运行配置的真实模型案例 | 用户显式授权，在独立 Local 环境执行 |

开发中可选择相关测试快速反馈；门禁与验收入口始终执行其完整范围。耗时超出目标时优化测试隔离、初始化与并行安排，并报告实际时间。

## AI 工作流程

1. 读取根 `AGENTS.md` 和 [文档索引](README.md)，核对 `docs/` 的实际文件，主动发现新增设计，再阅读与本次任务相关的文档及其引用。
2. 查看 Git 状态，确认改动范围和对应模块；发现他人的并行修改时先与用户确认。
3. 按相关设计执行 TDD，保持模块职责和 Dashboard 的 MVVM 分层，检查通过后原子提交。
4. 新增或调整文档时同步维护索引，操作复盘写入根 `Retrospective.md`。
5. 按用户授权执行推送、发布和真实模型调用，分别汇报已执行的本地检查、远端操作和 CI 结果。
