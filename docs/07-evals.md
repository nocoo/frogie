# 07 - Evals

## 评估目标

Evaluation 验证真实模型能否根据 Squad 的 MD、Skills 和 Workflow，通过 Pi Durable、工具与本地沙箱完成有证据的工作。

本地阶段复用 [Squads](05-squads.md) 中 `zeppelin` 的两个场景及一个恢复执行项，增加一个最小 hisfm 本地对话与历史检查，与既有场景同时执行来证明多项目隔离。通信阶段再运行 his.fm 的完整生产流程；不同验证目标沿用已有材料，不重复建立大套业务场景。

确定性机制由 [Tests](06-tests.md) 覆盖；本节要求真实模型调用、真实 Pi Harness、SQLite、工具回执和脚本执行。它们共同构成 MVP 的运行验收。

## 目录与执行路径

```text
evals/
  runner.ts
  zeppelin/
    cases/
      emergency-transit.md
      fleet-day.md
    fixtures/
      emergency-brief.md
      fleet-day-brief.md
    assertions.ts
  hisfm/
    cases/
      local-history.md
      podcast-production.md
    assertions.ts
```

用例 MD 描述 ID、Squad、工作方式、可选 Workflow、输入材料、预算和验收项。固定简报的 frontmatter 保存结构化数据，正文给出用户目标；断言从同一材料读取数值和约束。

恢复执行项是 `emergency-transit` 的中断配置，复用它的输入与业务断言。它使用 `--interrupt after-script-receipt` 选择下文的 E1-R 屏障，Dashboard 提供对应开关。评估代码和控制信息由宿主使用，Agent 获得任务简报、定义和预期交付格式。

CLI 规划入口为 `frogie eval <squad-id> --case <case-id> --allow-real-model`。Dashboard 的评估页调用同一个 runner，显示同一报告。执行路径为：

```text
用例与固定输入
  -> 冻结 Squad 和环境配置
  -> 本机 daemon + Core
  -> Pi Harness / SQLite / 真实 Models
  -> Conversation / Tool / 脚本沙箱
  -> 答复、产物和运行证据
  -> 确定性断言与 Dashboard 报告
```

每次真实评估在 Local 模式下新建独立环境、Harness 和数据库，由 Dashboard 全局切换器选中并观察。数据位于 `data/local/daemon/projects/<project-id>/environments/<environment-id>/harnesses/<harness-id>/`，恢复执行项重新打开本次数据库；普通案例之间保持独立。定义快照、原始输入、预期断言与实际输出分别保存并关联。

E2E 使用确定性模型与自己的隔离目录；真实评估使用用户明确选择的模型连接。评估入口从 `squads/` 或用户指定的定义导出加载快照，沿用相同解析与绑定规则。

`zeppelin` 验收使用从零搭建 E2E 全部检查点通过后导出的完整快照，三个执行项记录同一个定义摘要及对应通过报告。第二个 Squad 单独记录自己的摘要与实际角色配置。E2E 的虚构模型连接通过环境配置提供，真实评估另选获准模型并保留定义文件原样。

## 授权与预算

用户先确认模型连接、各角色的实际模型与思考等级、沙箱环境及调用预算。CLI 的显式选项或 Dashboard 的确认动作授权一次评估；批量执行逐项列出范围与合计上限。

每个执行项默认上限为 32 次模型请求、64 次工具进入和 8 分钟墙钟时间。计数包含子会话、压缩、重试和恢复尝试，恢复沿用已持久化的消耗与截止点。按 Core 的保守准入规则，提交后、发送前中断的模型预扣仍占用额度；工具回执命中也计一次进入，脚本物理执行次数单独记录。脚本仍使用 [Dashboard](04-dashboard.md) 的隔离和单次调用限制。

运行端提供请求计数和有界的模型输出设置；价格可用时展示费用估计和实际用量，未知时明确显示未知。额度通过新的用户确认调整，超限终止本次工作并保存已取得证据。

本地验收对每个候选版本执行三个 `zeppelin` 项，并将下面的 hisfm 本地检查合并到 E2 的观察窗口。修正后单独重跑受影响项，保留独立报告与版本。真实远端生产另行确认业务范围、模型及语音预算，不复用本地虚构输入。

## E1：紧急转场

### 输入与目标

工作方式为流程指导，使用 `emergency-transit` Workflow。舰队需在八小时内让三艘船穿过受干扰区域，保持生命支持、医疗与护航保障。

评估通过公共创建入口建立采用该 Workflow 的 `command` 会话，将其作为本次工作的主控。Pi 保留的 `root()` 会话与这次新建会话分别按各自 ID 识别。

简报固定以下能量数据，全部使用同一虚构单位，表示全舰队一次转场的总额：

| 项目 | 数值 |
| --- | --- |
| 可用能量 | 120 |
| 必须保留 | 20 |
| 生命支持 | 24 |
| 医疗 | 12 |
| 护航防护 | 14 |

| 路线 | 航行能耗 | 时间 |
| --- | --- | --- |
| `direct` | 58 | 4 小时 |
| `sheltered` | 44 | 6 小时 |
| `detour` | 25 | 10 小时 |

用户要求主控取得行动、工程和补给意见，分别计算三个候选预算并核对八小时约束，形成保留必要保障的转场方案。`operations` 进一步取得 `navigation` 与 `tactical` 的意见。执行顺序、并行安排和讨论次数由模型决定。

### 交付

主控通过 `write_artifact` 输出 `plan.md`，正文解释路线、保障安排和备选取舍。frontmatter 包含 `route`、按项目列出的 `allocations`、`reserve`、`remaining` 以及计算证据的 `ArtifactRef` ID。

资源计算脚本输出结构化结果。将必要负载与各路线能耗相加，三个候选预算依次得到：

| 路线 | 总需求 | 扣除保留后的剩余 | 时间约束 |
| --- | --- | --- | --- |
| `direct` | 108 | -8 | 满足 |
| `sheltered` | 94 | 6 | 满足 |
| `detour` | 75 | 25 | 超出 |

### 断言

- 本次主控会话采用 `command`；取得 `operations`、`engineering`、`logistics` 的真实子会话结果，`operations` 的派发关联到 `navigation` 和 `tactical`。
- 各会话具有自己的角色绑定与 Agent 配置，至少两种获准思考等级实际进入模型请求。
- `resource-budget/calculate` 在沙箱中成功执行，结果覆盖三个候选；计算输入可追溯到简报。
- `plan.md` 选择 `sheltered`，各必要分配和保留量满足输入，`remaining` 为 `6`，证据引用指向本次真实工具产物。
- 最终 Submission 为 `done`，answer entry 引用已保存方案；普通工作范围内的 Task 已终结。

这些断言证明定义装配、嵌套派发、工具执行、计算和产物回传的完整链路。正文允许不同表达，事实和证据按结构化数据检查。

## E2：舰队生活日

### 输入与目标

工作方式为自由发挥，由主控接收一份生活目标：给六十名船员安排休整、园艺活动和洗浴，照顾八名夜班人员及两名需要静养的人员。

简报提供以下约束，用水量表示全部相关人员的当日总额：

| 项目 | 要求 |
| --- | --- |
| 可用水量与保留 | 可用 `90`，保留 `10` |
| 基础居住与医疗用水 | 居住 `24`，医疗 `16` |
| 园艺活动 | 用水 `20`，安排连续两小时 |
| 洗浴选项 | 常规 `24`，节水 `12`，保留一种洗浴安排 |
| 活动窗口 | 园艺活动在 `14:00–21:00` 内完成 |
| 人员安排 | 夜班休息为 `08:00–14:00`，静养区域保留安静空间 |

主控自行安排专业协作，取得 `crew`、`medical`、`habitat` 和 `logistics` 的判断。该输入描述目标、约束和交付格式，模型选择步骤和交接方式。

### 交付与后续输入

首次输出 `day-plan.md`，包括生活安排、照护与人员约束、供水计划。frontmatter 包含 `shower`、活动 `schedule`、`allocations`、`reserve`、`remaining` 和计算证据引用。

满足约束的供水结果为节水洗浴，总需求 `72`，保留 `10`，剩余 `8`。活动时段可以在指定窗口内选择。

完成后，评估器向同一个主控 Conversation 提交新输入：“将园艺活动安排到 18:00–20:00，保持原供水方案和其他约束。”新的 Submission 应产生 `day-plan-revised.md`，并保留原产物可读。

后续输入前通过原生 Pi 压缩入口取得已提交摘要，再正常关闭并重启本次 Harness。报告保留压缩 Task、摘要、原会话身份，以及后续请求实际采用的压缩上下文。自动阈值和异常窗口由确定性集成测试覆盖。

### 断言

- 输入采用自由发挥模式，协作链包含主控到 `crew` 和 `logistics`、`crew` 到 `medical` 和 `habitat` 的真实派发。
- 医疗与居住的派发结果进入父会话后续模型请求的上下文，资源方案引用成功的计算结果。
- 最初方案的活动时段满足窗口与时长，水量分配满足照护、园艺、节水洗浴和保留量，剩余为 `8`。
- 后续输入使用同一主控 Conversation、不同 Submission，修订方案采用 `18:00–20:00`，保留供水与照护要求，并关联原方案。
- 两次输入均取得真实 answer entry；两版 Markdown 产物可以独立读取。
- 压缩后恢复同一会话，修订仍保留供水、照护约束与原产物引用，压缩调用计入同一预算。

该场景验证另一类业务目标、自由协作以及同一会话的连续工作。它与 E1 共同覆盖示例中的九个角色。

## E1-R：进程中断恢复

复用 E1 的定义、输入与全部业务断言，增加一次受控中断。

评估控制器与 Harness 子进程分开。故障注入点放在一次 `run_script` 调用已保存成功回执、Pi 尚未收到工具返回的位置；该调用属于工程或补给子会话。

1. 控制器等待已提交的子会话、输入和工具意图，记录原 Conversation、Submission 与 Tool Task ID。
2. 脚本执行器保存结果和幂等回执，在返回 Pi 前向控制器报告屏障并等待。
3. 控制器强制终止自己创建的 Harness 进程，Dashboard 和证据收集器继续运行。
4. 新进程按原版本重建 Registry、Models 和沙箱，打开同一 SQLite，完成预检后 `resume()`。
5. 被中断的安全工具重新进入时读取原回执，父派发继续等待原有子会话的结果，最终完成 E1。

恢复额外检查：

- 中断和新进程身份有记录，恢复读取原数据库与定义摘要。
- 中断前已有的 Conversation、Submission、Tool Task 继续使用，父子所有权保持一致。
- 被中断操作的容器启动次数为 `1`，恢复返回相同结果与产物引用；计数按该操作键归属。
- 客户端通过新快照恢复观察，最终 answer entry 和 `plan.md` 可见，普通任务排空。

容器启动次数由宿主执行器与外部控制器记录，模型响应不参与证明。恢复发起的新模型请求再次预扣，报告分别记录预算消耗与已确认用量，未回报费用标为未知；一次性断言针对已经完成并保存回执的工具效果。

注入屏障只存在于评估控制入口。若未触达指定工具边界，报告说明缺失证据；若启动条件失败，报告环境错误。默认 unsafe 工具的中断语义在确定性 L2 中覆盖。

## 本地双项目与历史检查

在 E2 的同一 daemon 中同时打开独立 `hisfm` Harness，保持所有业务远端断开。沿用其已保存角色和提示词，给主控一段由用户提供的本地编辑备忘，请其整理要点；后续输入要求总结本会话历史并引用备忘中的事实。

这一小检查与 E2 共用启动和观察过程，分别记录两组作用域和定义摘要，验证：

- 两个不同 Squad 均使用真实模型产生答复，活动时间存在交叠；可证明的子任务并行继续由 E1／E2 和确定性屏障测试提供。
- Dashboard 全局概览同时展示两组工作，可以进入主控、子会话、工具与产物；连接离线与本地运行状态独立。
- hisfm 的总结来自本地输入和历史，历史读取记录可追溯，不产生远端上下文或写回成功的伪回执。
- 两组的会话、产物、预算和模型配置保持隔离；第二次聊天恢复原 Conversation。
- 关闭 Dashboard 后工作继续；daemon 重启重新打开两份原数据库，历史与已有压缩状态可读。

直接调用 Role 和调试本地计算 Skill 的 UI 路径由 E2E 验证，真实脚本结果沿用 E1／E2。该检查只补多项目、本地历史及断线自治的证据。

## his.fm：远端生产闭环

通信阶段使用实际发布 SDK、本机 daemon 和云端 his.fm Gateway。先配对并验证两端状态，再从网站提交一个新的创作目标，按 [项目集成](09-project-integration.md) 完成选题、完善、人工确认、逐字稿、人工确认、音频生成及作品保存。

验收读取真实网站资料及版本、本地 Pi 记录、业务回执与音频文件：

- Frogie 主动建立认证连接，双方识别正确项目、环境、设备与协议；网站能实时查看子角色、工具进展和结果。
- 研究、写作、审阅和语音使用原角色及提示词；每次上下文读取记录资源版本，写回通过业务权限和版本检查。
- 结构化逐字稿、作品与音频真实存入 his.fm，音频可播放并记录实际时长；公开发布仍由拥有者另行确认。
- 异步语音子操作与原请求关联，终态由作品保存回执确认；“生成中”“本地完成”“网站已保存”分别可见。
- 在一个已持久化交付的安全边界中断连接，重新连接后查询原回执，验证最终写入不重复；更复杂故障窗口交给确定性测试。
- 本机恢复后保留同一会话、摘要与业务关联；网站离线 Agent 时基本业务可用，Frogie 与远端断开时仍可聊天与总结。

报告同时记录 SDK 包完整性、daemon 和网站版本、配对身份的非秘密标识、原用户请求及所有必需子操作、作品与文稿版本、音频摘要和业务回执。失去连接时没有取得证据的步骤明确保留未完成，不以最后一条模型回复替代验收。

第二类业务接入采用同样报告骨架，新增自己的输入与业务断言，不复制 Pi 恢复或通信故障用例。

## 评分与证据

自动评分采用确定性断言，读取实际 Pi 记录、工具回执和产物。模型最终回答是交付的一部分，执行证据来自宿主和持久化状态。

| 报告内容 | 用途 |
| --- | --- |
| 代码、Pi 版本、定义摘要、用例摘要和环境配置摘要 | 定位实际被评估的组合 |
| Local 模式与 `RuntimeScope` | 定位本次独立环境、Harness 与本地数据库 |
| 定义来源与可用时的 E2E 报告引用 | 将界面搭建结果与真实运行证据关联到同一份快照 |
| 各角色的 provider、modelId、thinkingLevel | 确认运行采用的 Agent 配置 |
| Conversation、Submission、Task 与 answer entry | 追踪实际执行和父子关系 |
| 工具参数、回执、脚本输入输出摘要与产物引用 | 校验计算、权限范围和结果来源 |
| 每条断言的结果、预期、实际值和证据链接 | 定位失败边界 |
| 请求次数、工具次数、用量、费用可知性、耗时与中断记录 | 核对预算及恢复代价 |

一次执行标为 `passed`、`failed` 或 `error`：所有必需断言满足为通过；执行取得结果但行为或证据未达标为失败；模型连接、版本、沙箱等执行条件异常为环境错误。中间阶段单独显示进行中的状态。

Markdown frontmatter 的解析复用定义解析工具，业务字段由案例断言校验。引用必须解析到当前环境已保存的产物，其摘要与工具记录一致。

人工验收只补充自动断言难以判断的部分：综合方案是否解释冲突，照护与生活安排是否可理解，Dashboard 能否从结论追到相关证据。人工意见随本次报告记录。

报告和必要证据存入对应 Harness 目录的 `evals/<evaluation-id>/`，随 `data/` 忽略，展示于 Dashboard，按 `RuntimeScope` 与关联 ID 读取原运行数据。导出前过滤凭据与无关路径，测试简报、定义、seed 与断言源码随 Git 管理。

## 分阶段评估闭环

1. Playwright 从空 E2E 工作区通过 Dashboard 搭建完整 `zeppelin`，保存并重新加载角色树、Skills、脚本与 Workflow 图，导出验收快照和报告。
2. 用户选择这份快照，在 Local 创建独立评估环境，配置真实模型和本地沙箱，确认权限、预算与九个角色的实际配置。
3. 运行 E1 与 E2，在 E2 同时执行 hisfm 本地历史检查；通过全局项目／Squad／Harness 入口观察派发、模型输出、脚本与产物。
4. 运行 E1-R，看到进程中断后的重连、原数据库中的会话恢复和最终交付。
5. 读取本地评估报告、对应 E2E 证据及人工 UI 验收结果。从失败证据调整定义或实现，再执行受影响的测试；定义改变后重新取得匹配摘要的搭建与评估证据。
6. 本地阶段通过后，以 SDK 符合性和包发布结果为前提，执行真实 his.fm 生产；再为第二类项目增加一条代表性业务验收。

每阶段以自己的全部必需断言、L1、关键 L2／L3 和人工验收作为完成依据。结论限定于报告记录的版本、环境和用例；本地验收、SDK 符合性与云端业务闭环分别成立，互不替代。
