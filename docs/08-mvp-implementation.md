# 08 - MVP 实施

## 实现起点

现有代码已经提供本地 Dashboard、Core 的 Pi 接入与 `openAgentHost`、SQLite 恢复及 `zeppelin`、`hisfm` 定义。his.fm 当前通过本地 tarball 依赖 Core，并在自己的进程中托管 Agent；其出站 WebSocket 与云端 AgentHub 是通信能力的复用基础。

目标架构将执行和历史集中到本机 daemon，业务项目依赖公开通信 SDK。已有命令和包的可用范围以根 `AGENTS.md`、`package.json` 与实际代码为准；本文中的 daemon 和 SDK 路径按下列阶段建立。

本轮先修改与审阅文档。文档确认后再实施本地阶段，各阶段验收通过后进入下一阶段，发布和真实业务效果经过对应授权。

## 阶段一：文档与契约审阅

统一项目、Squad、Harness、Role、Conversation、Submission、Task 的语义，明确本地与远端的数据权威、独立使用能力、权限和断线行为。模块分工见 [Core](03-core.md)、[Dashboard](04-dashboard.md)、[本地 Daemon](10-local-daemon.md) 与 [通信 SDK](11-communication-sdk.md)。

审阅重点：

- 原有运行与存储归属全部对齐 daemon，文档入口、目录和术语一致。
- 本地闭环可以在所有业务远端断开时成立；业务基本功能不依赖 Agent 在线。
- SDK 具备执行观察、历史、工具和业务回执，而非只有消息发送。
- 连接、Pi 执行与业务交付状态分开，权限、取消、恢复与副作用语义可测试。
- 实施次序、文件归属、质量门槛和真实验收明确，设计目标与已验证代码分开。

本轮文档按一个完整架构契约原子提交；后续审阅修正作为独立文档变更提交。代码、依赖、发布和运行数据在该阶段保持原样。

## 阶段二：Frogie 本机完整闭环

先让 Frogie 自己成为可用产品，远端连接保持可选。每个增量同时提供可操作入口与确定性测试。

| 增量 | 主要改动位置 | 可验收结果 |
| --- | --- | --- |
| 常驻宿主 | `apps/daemon/`、现有 `apps/dashboard/src/server/`、`packages/core/src/host/`、`scripts/dev.ts` | 执行、存储、模型和本地认证归 daemon；Dashboard 关闭后工作继续，单个 Harness 有界启停 |
| 项目与多 Harness | daemon 项目登记、存储与工作进程；`packages/core/src/runtime/`；`integrations/` | 同时运行至少两个不同项目的 Squad，登记完整本地扩展与工具 schema，数据库、权限、预算和故障隔离 |
| 管理与观察 | `apps/dashboard/src/models/`、`viewmodels/`、`views/` | 全局活动概览、项目切换、主控与指定角色聊天、任务图、工具、产物和压缩可追溯 |
| 定义与调试 | Dashboard 定义及画布、daemon 文件服务、`squads/`、`seeds/` | 角色、Skills、脚本与 Workflow 可编辑；Skill 使用真实执行器调试；新版本显式绑定 |
| 本地自治与恢复 | Core 历史读取、工具可用性、恢复及 daemon 生命周期 | 所有远端离线仍可聊天与总结历史；进程恢复使用原会话，压缩后继续工作 |
| 连接管理基础 | daemon 私有配置、Dashboard 项目连接页 | 可管理预期远端、凭据引用及权限，真实能力决定 UI 可用状态；网络握手在下一阶段完成 |

本阶段用现有 `zeppelin` 与 `hisfm` 验证两个业务不同的 Squad，沿用已有角色及提示词内容。迁入 `hisfm` 所需本地扩展和已声明工具 schema，回复、派发、工作检查、压缩和纯本地交付先完成自治；远端业务适配器在未配对时返回不可用。writer／reviewer 的 CodingTools 使用真实 OS 沙箱，其作品生产在下一阶段验证。具体工具分类见 [项目集成](09-project-integration.md)，材料见 [Squads](05-squads.md) 与 [Evals](07-evals.md)。

阶段完成条件：L1 通过；真实 Pi L2 证明两组隔离、并行、取消、恢复和压缩；Dashboard E2E 锁定完整定义搭建、两个项目管理与离线自治；真实模型评估分别取得答复与证据；人工验收看清哪些 Squad、角色和任务正在工作。

## 阶段三：通信 SDK 与 his.fm

### SDK 先通过独立验证

在 `packages/sdk/` 提取已验证的纯 DTO 与客户端，建立双向认证、Gateway、出站连接、可靠投递、查询订阅与业务工具契约。保留一个最小项目接入示例，分别测试 Node 客户端、浏览器客户端及 Cloudflare 适配。

客户端和 Gateway 以不同测试主体验证配对、授权、重连、续传、幂等、取消、异步子操作回传、慢消费者和协议不匹配。用实际打包产物检查依赖与秘密边界；通过后发布精确 SDK 版本，安装该版本完成消费测试。协议和发布验证见 [通信 SDK](11-communication-sdk.md)。

### his.fm 作为首个真实接入

本机 Connector 主动连接 his.fm Gateway，两端 UI 真实展示配对、连接和故障。Frogie 从网站读取当前资料，调度本机角色，将结构化结果通过网站业务控制器保存。完整流程包括选题、完善、人工确认、逐字稿、人工确认、真实音频生成和作品保存，细节见 [项目集成](09-project-integration.md)。

这一阶段将 his.fm 现有传输的共性归入 SDK，业务处理器留在 his.fm。Frogie 保留角色定义、本机扩展与执行脚本。his.fm 移除 Core tarball、Pi 依赖链与独立 Agent 宿主，使用精确 SDK 版本和锁文件。

切换在测试和真实验收准备完成后执行。先停接新 Agent 请求并收尾旧工作，保留业务数据和原本地历史原样，再启用新宿主；新宿主从当前业务上下文开始新的执行历史。旧执行数据的转换或删除需另行确认，目标运行路径只有 daemon。

阶段完成条件：两端离线基本功能独立；重新连接后权限与作用域正确；his.fm 可以从业务视角展开实际工具和任务进展；完整新作品有结构化保存回执和可播放音频；原用户请求等待全部必需子操作后进入明确终态；重试和恢复保持幂等。

## TDD、分工与提交

主控负责契约、依赖、文件归属、集成审查和提交。独立测试 agent 根据行为契约建立有效红灯，实现 agent 负责让测试通过；View agent 使用 Basalt 3.0.0 公开组件和官方 Recipes。模型与 agent 的选择在进入执行时依据实际任务决定。

当前增量的实现与下一增量的测试准备可以并行；同一文件由一个 agent 负责。单独审阅测试的输入、断言与失败原因，确认其来自契约而非复制实现细节。根配置、公开契约和 Git 操作由主控统一处理。

实现提交按上表的可用增量拆分，代码、对应测试与必要文档同次提交。跨仓变更分别原子提交，记录匹配的 SDK 版本；远端推送和发布各自取得明确授权。

## 统一验收要求

非 View 生产逻辑的语句、分支、函数和行覆盖率各至少 95%，类型、Biome lint 与格式检查零错误、零警告。Dashboard 采用 MVVM；纯展示 View 单列排除覆盖率，继续接受静态检查、E2E 与视觉验收。

所有容器、按钮与表单按 Basalt 3.0.0 组件和参考布局组合，专业画布使用 React Flow。保留淡绿色品牌、右上角 Local／E2E SegmentControl、左下角头像与正确表面层级。实例创建、订阅、取消与析构有界且可测试。

质量门禁以 [Tests](06-tests.md) 为准；真实模型、网络业务、音频和人工 UI 证据分别记录。每阶段保留实际版本、定义摘要、运行作用域和报告，完成结论只覆盖已经运行的链路。
